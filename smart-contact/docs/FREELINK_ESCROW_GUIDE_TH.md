## 1. ภาพรวมในหนึ่งนาที

### Escrow คืออะไร

**Escrow** คือ "คนกลางถือเงินไว้ก่อน" เหมือนฝากเงินไว้ที่ตู้เซฟกลาง

- ลูกค้า (client) ฝากเงินค่าจ้างเข้าตู้เซฟ → freelancer เห็นว่ามีเงินจริง เลยกล้าลงมือทำงาน
- ตู้เซฟจะไม่ยอมเปิดจนกว่าเงื่อนไขจะครบ (client ตรวจรับงาน หรือผู้ตัดสินสั่ง)
- ผลคือ client ไม่เสี่ยงจ่ายแล้วไม่ได้งาน และ freelancer ไม่เสี่ยงทำแล้วไม่ได้เงิน

ในระบบนี้ "ตู้เซฟ" ไม่ใช่คน แต่เป็นโปรแกรมที่อยู่บน blockchain เรียกว่า **Smart Contract** (เขียนด้วยภาษา **Solidity**) ใครก็แก้กติกาไม่ได้หลังจากวางขึ้นไปแล้ว

### ระบบนี้มี 3 ชิ้น

| ชิ้น | เปรียบเทียบ | ใครทำ | อยู่ที่ไหน |
| --- | --- | --- | --- |
| **Frontend** | หน้าร้าน (สิ่งที่ผู้ใช้เห็น กดปุ่ม) | ทำเสร็จแล้วในรูปแบบ mock | `freelink-marketplace.zip` |
| **Backend + Database** | หลังร้าน (เก็บข้อมูลงาน ผู้ใช้ ข้อเสนอ) | คนอื่นในทีม | ยังไม่มีในไฟล์ที่ผมได้รับ |
| **Smart Contract** | ตู้เซฟกลางบน blockchain | **งานของคุณ** | `BACKEND_START.md` |

### ใครทำอะไรได้ใน Contract

| บทบาท | คือใคร | ทำอะไรได้ |
| --- | --- | --- |
| **client** | ผู้จ้าง | ฝากเงิน, ปล่อยเงิน, ขอคืนเงิน (เฉพาะหลัง deadline และ freelancer ยังไม่ส่งงาน), เปิดข้อพิพาท |
| **freelancer** | ผู้รับจ้าง | ส่งงาน, ยอมคืนเงินให้ client ได้ทุกเมื่อ, เปิดข้อพิพาท |
| **arbiter** | ผู้ตัดสินข้อพิพาท (ฝั่งแพลตฟอร์ม) | ตัดสินว่าเงินไปทาง freelancer หรือคืน client |
| **owner** | คนที่ deploy contract | ตั้งค่าธรรมเนียม, เปลี่ยน arbiter, เปลี่ยนผู้รับค่าธรรมเนียม |

### เส้นทางของเงิน (flow ปกติ)

```
1) client อนุญาตให้ contract ดึงเหรียญ (approve)        ← เฉพาะแบบ ERC-20
2) client ฝากเงิน (depositEscrow)    → เงินเข้าตู้เซฟ      สถานะ: Funded
3) freelancer ทำงานเสร็จ กด ส่งงาน (submitWork)           (ยังไม่มีเงินขยับ แค่บันทึกว่าส่งแล้ว)
4) แยกเป็น 3 ทาง
   a) client พอใจ     → ปล่อยเงิน (releasePayment)   → freelancer ได้เงิน (หักค่าธรรมเนียม)   สถานะ: Released
   b) ตกลงกันไม่ได้   → เปิดข้อพิพาท (openDispute) → arbiter ตัดสิน (resolveDispute) → เงินไปทางใดทางหนึ่ง
   c) ยกเลิกงาน       → คืนเงิน (refundClient)       → เงินกลับ client                      สถานะ: Refunded
```

สถานะของเงินใน contract มี 5 แบบ: `Unfunded` (ยังไม่ฝาก) → `Funded` (ฝากแล้ว) → `Released` (จ่ายให้ freelancer แล้ว) / `Refunded` (คืน client แล้ว) / `Disputed` (มีข้อพิพาท เงินยังอยู่ในตู้เซฟ)

## 2. คำศัพท์ที่ควรรู้

| ศัพท์ | อธิบายแบบคนทั่วไป |
| --- | --- |
| **blockchain** | สมุดบัญชีกลางที่ทุกคนเห็นตรงกัน แก้ย้อนหลังไม่ได้ |
| **wallet** (เช่น **MetaMask**) | กระเป๋าเก็บเหรียญ + ใช้เซ็นยืนยันทุกการกระทำ ใครไม่มีกระเป๋าก็ใช้งานไม่ได้ |
| **address** | เลขที่บัญชีของ wallet หรือของ contract หน้าตาแบบ `0xAbC...1234` |
| **private key** | รหัสลับที่ใช้ควบคุม wallet ใครได้ไปคือเอาเงินในกระเป๋าไปได้หมด **ห้ามแชร์ ห้ามใส่ใน Git** |
| **Smart Contract** | โปรแกรมที่อยู่บน blockchain ทำงานตามกติกาที่เขียนไว้เป๊ะ ๆ |
| **deploy** | การเอา contract ขึ้นไปวางบน blockchain ทำแล้วได้ address ของ contract กลับมา และ **แก้โค้ดไม่ได้อีก** ถ้าจะแก้ต้อง deploy ตัวใหม่ (address ใหม่) |
| **ABI** | "คู่มือการใช้งาน" ของ contract บอกว่ามีปุ่ม (ฟังก์ชัน) อะไรบ้าง แต่ละปุ่มรับค่าอะไร Frontend ต้องมีไฟล์นี้ถึงจะเรียก contract ได้ |
| **mainnet** | เครือข่ายจริง ใช้เงินจริง |
| **testnet** | เครือข่ายซ้อมของปลอม เหรียญไม่มีมูลค่า (เช่น **Sepolia**) |
| **Chain ID** | เลขประจำตัวของแต่ละเครือข่าย Sepolia = `11155111` ใช้กันไม่ให้ส่งผิดเครือข่าย |
| **faucet** | ตู้กดเหรียญทดสอบฟรี (ใช้กับ testnet เท่านั้น) |
| **gas** | ค่าธรรมเนียมเครือข่าย ทุกครั้งที่ทำ transaction ต้องจ่าย เปรียบเหมือนค่าส่งพัสดุ จ่ายด้วยเหรียญหลักของเครือข่ายเสมอ (ETH) |
| **ETH / native currency** | เหรียญหลักของ Ethereum เป็นทั้งค่า gas และใช้เป็นเงินจ่ายตรง ๆ ได้ |
| **token / ERC-20** | เหรียญชนิดอื่นที่สร้างบน Ethereum โดยทำตามมาตรฐานชื่อ ERC-20 (เช่น USDC) |
| **stablecoin** | เหรียญที่ราคาผูกกับสกุลเงินจริง เช่น USDC ≈ 1 ดอลลาร์ ราคาไม่แกว่งเหมือน ETH |
| **mUSDC** | USDC ปลอมที่เราสร้างเองสำหรับทดสอบ (`MockUSDC`) ไม่มีมูลค่า |
| **approve** | การเซ็น "ใบมอบอำนาจ" ให้ contract ดึงเหรียญ ERC-20 จาก wallet เราได้ตามจำนวนที่ระบุ ต้องทำก่อนฝากเงิน (เหรียญ ERC-20 ส่งเข้า contract โดยตรงแบบ ETH ไม่ได้) |
| **decimals** | จำนวนตำแหน่งทศนิยมของเหรียญ contract เก็บเป็นจำนวนเต็มล้วน เช่น ETH = 18 ตำแหน่ง, USDC = 6 ตำแหน่ง |
| **transaction (tx)** | การกระทำหนึ่งครั้งบน blockchain ทุกครั้งต้องเซ็นใน wallet และเสีย gas |
| **transaction hash** | เลขอ้างอิงของ tx เอาไปเปิดดูใน explorer ได้ |
| **explorer** (เช่น **Etherscan**) | เว็บเปิดดู tx และ contract บน blockchain ของ Sepolia คือ `sepolia.etherscan.io` |
| **event** | "เสียงประกาศ/ใบเสร็จ" ที่ contract ปล่อยออกมาเมื่อมีเรื่องสำคัญเกิดขึ้น (เช่น `PaymentReleased`) Backend ฟัง event เพื่ออัปเดตฐานข้อมูล |
| **revert** | contract ปฏิเสธการกระทำ เพราะผิดเงื่อนไข (เช่นคนที่ไม่ใช่ client มากด ปล่อยเงิน) tx ล้มเหลว |
| **arbiter** | ผู้ตัดสินข้อพิพาท |
| **multisig** | wallet ที่ต้องมีหลายคนเซ็นพร้อมกันถึงจะสั่งงานได้ (เปรียบเหมือนตู้เซฟที่ต้องใช้กุญแจหลายดอก) |
| **milestone** | งวดงาน แบ่งงานใหญ่เป็นหลายงวด จ่ายเป็นงวด ๆ |
| **bps (basis points)** | หน่วยเปอร์เซ็นต์ละเอียด 100 bps = 1% ดังนั้น `250` = 2.5%, `1000` = 10% |
| **hash / keccak256** | เครื่องย่อยข้อความเป็นรหัสความยาวคงที่ แปลงไปได้ทางเดียว **ย้อนกลับไม่ได้** |
| **bytes32** | ชนิดข้อมูลรหัสยาว 32 ไบต์ ที่ contract ใช้แทน id (ผลลัพธ์ของ hash) |
| **RPC URL** | ที่อยู่ "ประตู" ที่โปรแกรมใช้คุยกับ blockchain |
| **Hardhat / Remix** | เครื่องมือเขียน ทดสอบ และ deploy contract (Remix = ในเบราว์เซอร์, Hardhat = ในเครื่องเรา) |
| **audit** | การให้ผู้เชี่ยวชาญตรวจช่องโหว่ของ contract ก่อนใช้กับเงินจริง contract นี้ **ยังไม่ผ่าน audit** |

## 3. โค้ดสองฝั่งตอนนี้ยังไม่ตรงกันตรงไหนบ้าง

`BACKEND_START.md` เขียนไว้เองว่า "ชื่อฟังก์ชันและพารามิเตอร์เป็นข้อเสนอ ยังไม่ได้ตกลงกับทีม" พอผมเทียบกับโค้ด Frontend จริงก็เจอจุดที่ยังไม่ตรงกัน 10 จุด **ตรงนี้คือเหตุผลที่ข้อ 9 สำคัญ**

| # | เรื่อง | Frontend ตอนนี้ | Contract ใน md | ต้องทำอะไร | ดูข้อ |
| --- | --- | --- | --- | --- | --- |
| 1 | สกุลเงิน | ทั้งเว็บแสดงเป็น **บาท** และส่งตัวเลขบาทเข้า `parseUnits` ตรง ๆ โดยไม่แปลง รองรับเฉพาะ ETH ตรง ๆ (ถ้า ERC-20 โยน error ว่า "ยังไม่ได้เตรียม approve") | ERC-20 (mUSDC, 6 decimals) | เลือกแบบ A/B และกำหนดวิธีแปลงบาทเป็นเหรียญ | 9.1 |
| 2 | ฟังก์ชันฝากเงิน | ส่งแค่ `(projectId, {value})` | `depositEscrow(projectId, freelancer, amount, deadline)` และไม่ใช่ `payable` | แก้ให้ตรงกันทั้งสองฝั่ง | 9.2 |
| 3 | รหัสโปรเจกต์ | ส่ง `project.id` (ข้อความ) ตรง ๆ | ต้องเป็น `bytes32` | ต้องแปลงด้วย `ethers.id(project.id)` ไม่งั้น ethers จะ error | 9.8 |
| 4 | ค่าธรรมเนียม | **5%** บวก **เพิ่ม** จากยอดงาน (client จ่ายเพิ่ม) | **2.5%** หัก **ออก** จากยอดที่ฝาก (freelancer ได้น้อยลง) | เลือกกติกาเดียว | 9.4 |
| 5 | เปิดข้อพิพาท | `openDispute(projectId, reason)` | `openDispute(projectId)` ไม่มี reason | ตัดสินใจว่าเหตุผลเก็บที่ไหน (แนะนำเก็บใน DB) | 9.2 |
| 6 | wallet ของ freelancer | **ไม่มีเก็บไว้ในข้อมูลใด ๆ เลย** | ต้องใช้ตอนฝากเงิน | Backend ต้องเพิ่มช่อง `walletAddress` ให้ freelancer เชื่อม wallet ในโปรไฟล์ | 9.2 |
| 7 | "ส่งงาน/ตรวจรับ" | ปุ่มพวกนี้เรียกแค่ API (เปลี่ยนสถานะในฐานข้อมูล) **ไม่เรียก contract** ส่วนปุ่มปล่อยเงินจริงอยู่อีกหน้า (Escrow) | `submitWork`, `releasePayment` อยู่บน chain | ต้องกำหนดว่า "ใครคือความจริง" (ดูหมายเหตุใต้ตาราง) | 9.2 / 9.6 |
| 8 | Milestone | หน้าโครงการแสดง milestone พร้อมยอดเงินแต่ละงวด | จ่ายก้อนเดียวต่อโปรเจกต์ | เลือกวิธีรับมือ | 9.5 |
| 9 | ข้อพิพาท/คืนเงิน | ไม่มีปุ่มและไม่มีหน้าเลย และ `escrowStatus` มีแค่ 4 ค่า (ไม่มี disputed) | มีครบ + มีสถานะ `Disputed` | เพิ่ม UI หรือตกลงว่า demo ยังไม่ทำ | 9.3 / 9.6 |
| 10 | decimals | ค่าเริ่มต้น **18** | mUSDC = **6** | ตั้งให้ตรงกับเหรียญ ถ้าลืมยอดจะเพี้ยน 10¹² เท่า | 9.1 |

**หมายเหตุข้อ 7 (ทำไมสำคัญ):** ตอนนี้ปุ่ม "ตรวจรับงาน" ใน Frontend แค่สั่ง API ให้เปลี่ยนสถานะเป็น "จ่ายแล้ว" โดยที่เงินจริงบน chain ยังไม่ขยับ ถ้าต่อของจริงโดยไม่แก้ จะเกิดกรณี "หน้าเว็บบอกจ่ายแล้ว แต่เงินยังอยู่ในตู้เซฟ" ได้ แนวทางที่ปลอดภัยคือ **ถือ blockchain เป็นความจริงเรื่องเงิน** แล้วให้ Backend ฟัง event (เช่น `PaymentReleased`) เพื่ออัปเดตฐานข้อมูล ไม่ใช่ให้ Backend ตั้งสถานะเองก่อน ซึ่งตรงกับ checklist ใน `INTEGRATION.md` ที่เขียนว่า "Notification เกิดจาก event จริง" และ "ไม่มีปุ่มที่แจ้งสำเร็จปลอม"
