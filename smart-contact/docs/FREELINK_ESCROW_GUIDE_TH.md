## 1. ภาพรวมในหนึ่งนาที

### Escrow คืออะไร

**Escrow** คือ "คนกลางถือเงินไว้ก่อน" เหมือนฝากเงินไว้ที่ตู้เซฟกลาง

- ลูกค้า (client) ฝากเงินค่าจ้างเข้าตู้เซฟ → freelancer เห็นว่ามีเงินจริง เลยกล้าลงมือทำงาน
- ตู้เซฟจะไม่ยอมเปิดจนกว่าเงื่อนไขจะครบ (client ตรวจรับงาน, หมดเวลาตรวจรับ หรือผู้ตัดสินสั่ง)
- ผลคือ client ไม่เสี่ยงจ่ายแล้วไม่ได้งาน และ freelancer ไม่เสี่ยงทำแล้วไม่ได้เงิน

ในระบบนี้ "ตู้เซฟ" ไม่ใช่คน แต่เป็นโปรแกรมที่อยู่บน blockchain เรียกว่า **Smart Contract** (เขียนด้วยภาษา **Solidity**) ใครก็แก้กติกาไม่ได้หลังจากวางขึ้นไปแล้ว

### ระบบนี้มี 3 ชิ้น

| ชิ้น | เปรียบเทียบ | ใครทำ | อยู่ที่ไหน |
| --- | --- | --- | --- |
| **Frontend** | หน้าร้าน (สิ่งที่ผู้ใช้เห็น กดปุ่ม) | ทำเสร็จแล้วในรูปแบบ mock | `freelink-marketplace.zip` |
| **Backend + Database** | หลังร้าน (เก็บข้อมูลงาน ผู้ใช้ ข้อเสนอ) | คนอื่นในทีม | ยังไม่มีในไฟล์ที่ผมได้รับ |
| **Smart Contract** | ตู้เซฟกลางบน blockchain | **งานของคุณ** | `contracts/FreelinkEscrow.sol` (อธิบายใน `BACKEND_START_ver_0_2.md`) |

### ใครทำอะไรได้ใน Contract

| บทบาท | คือใคร | ทำอะไรได้ |
| --- | --- | --- |
| **client** | ผู้จ้าง | ฝากเงิน, ปล่อยเงิน, ขอให้แก้งาน (`requestRevision` จำกัดจำนวนครั้ง) หรือปฏิเสธงาน (เปิดข้อพิพาท) ภายในช่วงตรวจรับ, ขอคืนเงิน (ก่อน freelancer ยอมรับได้ทุกเมื่อ หลังยอมรับต้องรอเลย deadline และงานต้องยังไม่ถูกส่ง) |
| **freelancer** | ผู้รับจ้าง | ยอมรับงาน, ส่งงาน (ก่อน deadline), เบิกเงินเองถ้า client เงียบเกินช่วงตรวจรับ, ยอมคืนเงินให้ client ได้ทุกเมื่อ, เปิดข้อพิพาท (เฉพาะตอนกำลังทำงานและก่อน deadline) |
| **arbiter** | ผู้ตัดสินข้อพิพาท (ฝั่งแพลตฟอร์ม) | ตัดสินแบ่งเงินเป็นสัดส่วน 0–100% ระหว่าง freelancer กับ client |
| **owner** | คนที่ deploy contract | ตั้งค่าธรรมเนียม, เปลี่ยน arbiter, เปลี่ยนผู้รับค่าธรรมเนียม (มีผลกับรายการใหม่เท่านั้น **แตะเงินใน escrow ที่ฝากไปแล้วไม่ได้**) |
| **ใครก็ได้** | — | อ่านข้อมูล, เบิกยอดค้างของตัวเอง (`withdraw`) |

### เส้นทางของเงิน (flow ปกติ)

```
1) client ฝากเงิน (depositEscrow)  แนบ ETH = ค่าจ้าง + ค่าธรรมเนียม       สถานะ: Funded
        ↳ ก่อนขั้นต่อไป client หรือ freelancer ยกเลิกแล้วรับ/คืนเงินเต็มได้ทันที
2) freelancer ยอมรับงาน (acceptEscrow) ยืนยันข้อตกลงฉบับเดียวกัน (termsHash)   สถานะ: Active
3) freelancer ส่งงาน (submitWork) ก่อน deadline → เริ่มนับ "ช่วงตรวจรับ"       สถานะ: Submitted
4) ภายในช่วงตรวจรับ แยกเป็น 5 ทาง
   a) client พอใจ        → ปล่อยเงิน (releasePayment)         → Released
   b) client ไม่พอใจ     → ปฏิเสธงาน (openDispute) → arbiter ตัดสิน (resolveDispute) → Resolved
   c) client เงียบ       → พ้นช่วงตรวจรับ freelancer เบิกเอง (claimAfterReview)    → Released
   d) arbiter เงียบนาน   → คู่กรณีสั่งแบ่งครึ่ง (settleExpiredDispute)           → Resolved
   e) client ขอให้แก้   → ขอแก้งาน (requestRevision) กลับ Active + ขยายเวลา → freelancer ส่งใหม่ (วนได้ไม่เกินที่กำหนด ค่าเริ่มต้น 2 ครั้ง) → Submitted
5) ยกเลิกงาน (refundClient) → เงินกลับ client เต็มจำนวน รวมค่าธรรมเนียม           → Refunded
```

สถานะของเงินใน contract มี 8 แบบ:

| เลข | สถานะ | ความหมาย |
| --- | --- | --- |
| 0 | `Unfunded` | ยังไม่ฝาก |
| 1 | `Funded` | ฝากแล้ว รอ freelancer ยอมรับ |
| 2 | `Active` | freelancer ยอมรับแล้ว กำลังทำงาน หรือกำลังแก้งานหลัง client ขอแก้ (ดู `revisionCount`) |
| 3 | `Submitted` | ส่งงานแล้ว อยู่ในช่วงตรวจรับ |
| 4 | `Disputed` | มีข้อพิพาท เงินยังอยู่ในตู้เซฟ รอ arbiter |
| 5 | `Released` | จ่าย freelancer เต็มจำนวนแล้ว |
| 6 | `Refunded` | คืน client เต็มจำนวนแล้ว |
| 7 | `Resolved` | ปิดด้วยคำตัดสิน (หรือ timeout) ดูสัดส่วนที่ `payoutBps` |

### เงินไหลอย่างไร (ตัวอย่าง: ค่าจ้าง 1 ETH, ค่าธรรมเนียม 5%)

| เหตุการณ์ | client | freelancer | แพลตฟอร์ม |
| --- | --- | --- | --- |
| ฝาก | จ่าย **1.05** | — | — |
| ปล่อยเงิน / เบิกหลังช่วงตรวจรับ | — | ได้ **1.00** | ได้ **0.05** |
| คืนเงิน | ได้คืน **1.05** เต็ม | — | ไม่ได้ |
| arbiter ตัดสิน freelancer 60% | ได้ 0.42 | ได้ 0.60 | ได้ 0.03 |
| arbiter เงียบ → แบ่งครึ่ง | ได้ 0.525 | ได้ 0.50 | ได้ 0.025 |

ค่าธรรมเนียมแพลตฟอร์มคิดเฉพาะส่วนที่จ่ายให้ freelancer จริง ส่วนที่เหลือทั้งหมดคืน client และค่าธรรมเนียมถูกเก็บ (snapshot) ตอนฝาก ถ้า owner เปลี่ยนอัตราทีหลังจะไม่กระทบเงินที่ฝากไปแล้ว

## 2. คำศัพท์ที่ควรรู้

| ศัพท์ | อธิบายแบบคนทั่วไป |
| --- | --- |
| **blockchain** | สมุดบัญชีกลางที่ทุกคนเห็นตรงกัน แก้ย้อนหลังไม่ได้ |
| **wallet** (เช่น **MetaMask**) | กระเป๋าเก็บเหรียญ + ใช้เซ็นยืนยันทุกการกระทำ ใครไม่มีกระเป๋าก็ใช้งานไม่ได้ |
| **address** | เลขที่บัญชีของ wallet หรือของ contract หน้าตาแบบ `0xAbC...1234` |
| **private key** | รหัสลับที่ใช้ควบคุม wallet ใครได้ไปคือเอาเงินในกระเป๋าไปได้หมด **ห้ามแชร์ ห้ามใส่ใน Git** |
| **Smart Contract** | โปรแกรมที่อยู่บน blockchain ทำงานตามกติกาที่เขียนไว้เป๊ะ ๆ |
| **deploy** | การเอา contract ขึ้นไปวางบน blockchain ทำแล้วได้ address ของ contract กลับมา และ **แก้โค้ดไม่ได้อีก** ถ้าจะแก้ต้อง deploy ตัวใหม่ (address ใหม่) |
| **ABI** | "คู่มือการใช้งาน" ของ contract บอกว่ามีปุ่ม (ฟังก์ชัน) อะไรบ้าง แต่ละปุ่มรับค่าอะไร Frontend ต้องมีไฟล์นี้ถึงจะเรียก contract ได้ |
| **mainnet** | เครือข่ายจริง ใช้เงินจริง |
| **testnet** | เครือข่ายซ้อมของปลอม เหรียญไม่มีมูลค่า (เช่น **Sepolia**) |
| **Chain ID** | เลขประจำตัวของแต่ละเครือข่าย Sepolia = `11155111` ใช้กันไม่ให้ส่งผิดเครือข่าย |
| **faucet** | ตู้กดเหรียญทดสอบฟรี (ใช้กับ testnet เท่านั้น) |
| **gas** | ค่าธรรมเนียมเครือข่าย ทุกครั้งที่ทำ transaction ต้องจ่าย เปรียบเหมือนค่าส่งพัสดุ จ่ายด้วย ETH เสมอ |
| **ETH / native currency** | เหรียญหลักของ Ethereum ใช้เป็นทั้งค่า gas และเงินค่าจ้างในระบบนี้ (บน Sepolia เป็นของปลอมไม่มีมูลค่า) ไม่ต้อง `approve` ไม่ต้องมี token อื่น |
| **wei** | หน่วยย่อยสุดของ ETH: 1 ETH = 10¹⁸ wei contract คิดเป็น wei เสมอ |
| **msg.value** | จำนวน ETH ที่แนบมากับ transaction ในระบบนี้ต้องเท่ากับ "ค่าจ้าง + ค่าธรรมเนียม" **พอดี** ไม่งั้น transaction ล้ม |
| **transaction (tx)** | การกระทำหนึ่งครั้งบน blockchain ทุกครั้งต้องเซ็นใน wallet และเสีย gas |
| **transaction hash** | เลขอ้างอิงของ tx เอาไปเปิดดูใน explorer ได้ |
| **explorer** (เช่น **Etherscan**) | เว็บเปิดดู tx และ contract บน blockchain ของ Sepolia คือ `sepolia.etherscan.io` |
| **event** | "เสียงประกาศ/ใบเสร็จ" ที่ contract ปล่อยออกมาเมื่อมีเรื่องสำคัญเกิดขึ้น (เช่น `PaymentReleased`) Backend ฟัง event เพื่ออัปเดตฐานข้อมูล |
| **revert** | contract ปฏิเสธการกระทำ เพราะผิดเงื่อนไข (เช่นคนที่ไม่ใช่ client มากดปล่อยเงิน) tx ล้มเหลว |
| **arbiter** | ผู้ตัดสินข้อพิพาท |
| **escrowId** | รหัสของเงินแต่ละก้อน = hash ของ (address ของ client + `projectId`) ทุกฟังก์ชันหลังฝากเงินใช้รหัสนี้ ไม่ใช่ `projectId` ตรง ๆ เรียก `computeEscrowId` เพื่อให้ contract คำนวณให้ได้ |
| **termsHash** | "ลายนิ้วมือ" ของข้อตกลง (ขอบเขตงาน ราคา ฯลฯ) ที่เก็บนอก chain client ใส่ตอนฝาก freelancer ต้องส่งค่าเดียวกันตอนยอมรับ เป็นหลักฐานว่าสองฝ่ายเห็นข้อตกลงฉบับเดียวกัน |
| **deadline** | เส้นตายส่งงาน (เวลา unix) ส่งช้าไปแม้วินาทีเดียวจะส่งผ่าน contract ไม่ได้ |
| **ช่วงตรวจรับ** (`reviewPeriod`) | เวลาที่ client มีหลัง freelancer ส่งงาน เพื่อปล่อยเงินหรือปฏิเสธ ถ้าเงียบ freelancer เบิกเงินเองได้ |
| **requestRevision** | ฟังก์ชันที่ client ใช้ "ขอให้แก้งาน" ระหว่างช่วงตรวจรับ สถานะกลับเป็น `Active` แล้ว freelancer ส่งงานใหม่ได้ |
| **revisionPeriod** | เวลาขั้นต่ำที่ freelancer มีส่งงานแก้หลังถูกขอแก้ ตั้งตอน deploy แก้ไม่ได้ (`immutable`) contract เป็นคนกำหนด deadline ใหม่ ไม่ใช่ client |
| **maxRevisions** / **revisionCount** | จำนวนครั้งสูงสุดที่ client ขอแก้ได้ต่อ escrow / จำนวนครั้งที่ขอไปแล้ว (นับต่อเนื่อง ไม่รีเซ็ตเมื่อส่งซ้ำ) |
| **snapshot** | บันทึกค่า ณ ขณะนั้นไว้ ค่าธรรมเนียมและ arbiter ถูก snapshot ตอนฝาก/ตอนเปิดข้อพิพาท การเปลี่ยนค่าทีหลังไม่ย้อนกระทบ |
| **immutable** | ค่าที่ตั้งตอน deploy แล้วแก้ไม่ได้อีก (`reviewPeriod`, `arbiterTimeout`, `revisionPeriod`, `maxRevisions`) |
| **pull payment / `withdraw`** | ถ้าผู้รับเป็น contract ที่ปฏิเสธรับ ETH contract จะ "พักยอดไว้" ให้ผู้รับมาเบิกเอง แทนที่จะให้ทั้ง transaction ล้ม (กระเป๋าปกติได้เงินทันทีเหมือนเดิม) |
| **multisig** | wallet ที่ต้องมีหลายคนเซ็นพร้อมกันถึงจะสั่งงานได้ (เปรียบเหมือนตู้เซฟที่ต้องใช้กุญแจหลายดอก) |
| **milestone** | งวดงาน แบ่งงานใหญ่เป็นหลายงวด จ่ายเป็นงวด ๆ |
| **bps (basis points)** | หน่วยเปอร์เซ็นต์ละเอียด 100 bps = 1% ดังนั้น `500` = 5%, `10000` = 100% |
| **hash / keccak256** | เครื่องย่อยข้อความเป็นรหัสความยาวคงที่ แปลงไปได้ทางเดียว **ย้อนกลับไม่ได้** |
| **bytes32** | ชนิดข้อมูลรหัสยาว 32 ไบต์ ที่ contract ใช้แทน id (ผลลัพธ์ของ hash) |
| **RPC URL** | ที่อยู่ "ประตู" ที่โปรแกรมใช้คุยกับ blockchain |
| **Hardhat / Remix** | เครื่องมือเขียน ทดสอบ และ deploy contract (Remix = ในเบราว์เซอร์, Hardhat = ในเครื่องเรา โปรเจกต์นี้ใช้ Hardhat 3) |
| **keystore** | ที่เก็บค่าลับ (RPC URL, private key) แบบเข้ารหัสของ Hardhat จึงไม่ต้องเขียนลงไฟล์ในโปรเจกต์ |
| **audit** | การให้ผู้เชี่ยวชาญตรวจช่องโหว่ของ contract ก่อนใช้กับเงินจริง contract นี้ **ยังไม่ผ่าน audit** |

## 4. ข้อ 10 ทีละข้อ

ข้อนี้คือรายการ "ต้องตกลงกับทีมก่อน deploy จริง" ใน `BACKEND_START_ver_0_2.md` หัวข้อ 10 แต่ละข้อบอก 4 อย่าง: **คืออะไร**, **ตอนนี้ contract ทำอะไร**, **ตัวเลือก**, **แนะนำ (ความเห็น ไม่ใช่การตัดสินใจ)** ข้อที่มี ✔ คือตัดสินใจหรือแก้ไปแล้วใน v2

### ✔ 4.0 ที่ตกลง/แก้ไปแล้ว (ไม่ต้องตัดสินใจซ้ำ ยกเว้นทีมไม่เห็นด้วย)

- **สกุลเงิน = native ETH บน Sepolia** เพราะ Frontend รองรับเฉพาะ native อยู่แล้ว ฝากครั้งเดียวไม่ต้อง approve
- **client หายไปหลังส่งงาน** แก้แล้ว เงินไปหา freelancer อัตโนมัติหลังพ้นช่วงตรวจรับผ่าน `claimAfterReview` (ฉบับเดิมเป็นข้อที่ยังไม่มีทางออก)
- **ขอแก้งานหลังส่ง** ตัดสินใจแล้ว (31 ต.ค. 2026) ให้ client ขอแก้ได้ **2 ครั้งต่อ escrow** (ส่งงานได้สูงสุด 3 รอบ) และ freelancer มีเวลาส่งใหม่อย่างน้อย **7 วัน** รายละเอียดและเหตุผลในข้อ 4.9 ค่าทั้งสองตั้งตอน deploy และแก้ไม่ได้หลังจากนั้น

### 4.1 รูปแบบการเรียกฝากเงิน (ฝั่ง Frontend ต้องแก้)

**คืออะไร:** ฝากเงินต้องส่ง 5 ค่า และแนบ ETH ให้ตรงยอด

**ตอนนี้ contract ทำอะไร:** `depositEscrow(projectId, freelancer, deadline, termsHash, amount)` ต้องแนบ `amount + ค่าธรรมเนียม` **พอดี** ถ้าไม่ตรงจะ revert `WrongPayment(expected, sent)` ไม่เดาแทน client เรียก `quote(amount)` ก่อนเพื่อรู้ยอดรวม

**ข้อควรระวัง:** ถ้า owner เปลี่ยนค่าธรรมเนียมในจังหวะเดียวกับที่ client กดฝาก transaction จะล้ม (ปลอดภัยกว่าจ่ายผิดยอดเงียบ ๆ) UI ต้องรองรับ "ดึง quote ใหม่แล้วกดอีกครั้ง"

**แนะนำ:** ทำตามตัวอย่างโค้ดใน `BACKEND_START_ver_0_2.md` หัวข้อ 8.3

### 4.2 ความยาวช่วงตรวจรับ `reviewPeriod`

**คืออะไร:** เวลาที่ client มีหลัง freelancer ส่งงาน เพื่อปล่อยเงินหรือปฏิเสธ ถ้าเงียบ freelancer เบิกเองได้

**ตอนนี้ contract ทำอะไร:** ตั้งตอน deploy (`REVIEW_PERIOD_SECONDS` ค่าเริ่มต้น 7 วัน = 604800) **แก้ไม่ได้หลัง deploy** ได้ตั้งแต่ 1 วินาทีถึง 30 วัน

| ตัวเลือก | ข้อดี | ข้อเสีย |
| --- | --- | --- |
| สั้น (เช่น 3 วัน) | freelancer ไม่ต้องรอนาน | client ที่ไม่ได้เข้าเว็บทุกวันอาจพลาด |
| ยาว (เช่น 14 วัน) | client สบาย | freelancer รอเงินนาน |

**แนะนำ:** ค่าจริงให้ทีมตัดสิน (เริ่มที่ 7 วัน) แต่สำหรับ **การ demo** ให้ deploy contract อีกชุดที่ตั้งค่าสั้น ๆ (เช่น 5–10 นาที) จะได้โชว์ทั้งกรณี "client เงียบ" และ "พ้นช่วงตรวจรับ" ได้สด ๆ โดยไม่ต้องรอ ตัวที่แสดงให้คนนอกดูกับตัวที่เป็นค่าตั้งจริงควรแยกกัน และ UI ต้องมีระบบแจ้งเตือน client ก่อนหมดเวลา

### 4.3 ความยาว `arbiterTimeout` และผลแบ่งครึ่ง

**คืออะไร:** ถ้า arbiter ไม่ตัดสินภายในเวลาที่กำหนด คู่กรณีฝ่ายใดก็สั่งให้ **แบ่งครึ่ง** ได้ เพื่อไม่ให้เงินค้างตลอดไป

**ตอนนี้ contract ทำอะไร:** ตั้งตอน deploy (`ARBITER_TIMEOUT_SECONDS` ค่าเริ่มต้น 14 วัน) แก้ไม่ได้หลัง deploy ได้ตั้งแต่ 1 วินาทีถึง 90 วัน ผล timeout คือ freelancer 50% / client 50% (ค่าธรรมเนียมคิดตามสัดส่วน)

**ทำไมถึง 50/50:** ถ้าเอนไปทางใดทางหนึ่ง ฝ่ายนั้นจะอยากให้ arbiter เงียบ แบ่งครึ่งทำให้ทั้งสองฝ่ายอยากให้ arbiter ตัดสิน

**ที่ต้องถามทีม:** รับผล 50/50 ได้ไหม และ arbiter ต้องตัดสินภายในกี่วัน (ข้อ 4.7)

**แนะนำ:** ตั้งให้ยาวกว่าเวลาที่ทีมตอบข้อพิพาทได้จริงอย่างสบาย ๆ ส่วน demo ตั้งสั้นเหมือนข้อ 4.2

### 4.4 สูตร `termsHash` (ทีมต้องตกลง)

**คืออะไร:** hash ของข้อตกลงที่ทั้งสองฝ่ายเห็นตรงกัน client ผูกไว้ตอนฝาก freelancer ต้องส่งค่าเดียวกันตอนยอมรับ ถ้าไม่ตรง `acceptEscrow` จะ revert `InvalidTerms` และ arbiter ใช้เป็นหลักฐานอ้างอิง

**ต้องตัดสินใจ 2 เรื่อง:** (1) hash อะไรบ้าง (เช่น ชื่องาน + ขอบเขต + ราคา + deadline) (2) เก็บข้อความต้นฉบับไว้ที่ไหนให้ arbiter เปิดเทียบได้

**ข้อควรระวัง (พลาดง่าย):** อย่า hash ผลของ `JSON.stringify` ที่สร้างใหม่จากฟอร์มในแต่ละฝั่ง เพราะลำดับ key หรือเลขทศนิยมต่างกันนิดเดียว hash จะต่างทั้งหมด

**แนะนำ:** ให้ Backend สร้างข้อความข้อตกลงฉบับเดียว (ข้อความ/JSON ที่เรียงคงที่) เก็บใน DB แล้วคำนวณ hash จาก **ข้อความที่เก็บไว้นั้นเอง** ทั้ง client และ freelancer ดึงข้อความเดียวกันไป hash ไม่ต้องคำนวณใหม่จากฟอร์ม

### 4.5 วิธีแปลงบาท → ETH

**คืออะไร:** UI ทั้งเว็บคิดเป็นบาท แต่ contract รับเป็น ETH (หน่วย wei)

**ตัวเลือก:**
- **อัตราคงที่ในไฟล์ config** (เช่น 1 ETH = X บาท) ง่ายที่สุด เหมาะกับ demo บน Sepolia ที่ ETH ไม่มีมูลค่าอยู่แล้ว
- **ดึงราคาจริงจาก price oracle** ถูกต้องกว่าแต่ซับซ้อนกว่ามาก ไม่จำเป็นสำหรับ demo

**ข้อควรระวัง:** แปลงให้เสร็จก่อนฝากแล้ว **ล็อกยอด wei ตอนฝาก** หลังจากนั้นยอดบน chain ไม่เปลี่ยนตามอัตรา และ UI ควรแสดงอัตราที่ใช้ให้ผู้ใช้เห็น ตัวอย่างโค้ดปัดเป็นทศนิยม 6 ตำแหน่งก่อน `parseEther` เพื่อกัน error เรื่องทศนิยมยาว

**แนะนำ:** อัตราคงที่

### 4.6 ค่าธรรมเนียมและผู้รับ

**ตอนนี้ contract ทำอะไร:** 5% บวกเพิ่ม (`FEE_BPS=500`) ตรงกับ UI เพดาน 10% ผู้รับตั้งตอน deploy (`FEE_RECIPIENT_ADDRESS`) และ owner เปลี่ยนได้ภายหลัง (มีผลกับรายการใหม่เท่านั้น)

**ที่ต้องถามทีม:** ยืนยัน 5% บวกเพิ่มหรือเปลี่ยน และ address ผู้รับเป็นของใคร

**แนะนำ:** ใช้ wallet ของทีมที่ไม่ใช่ wallet ที่ใช้ deploy และให้ Frontend เรียก `quote()` แทนค่าที่ฮาร์ดโค้ด

### 4.7 ใครเป็น arbiter และต้องตัดสินกี่วัน

**ตอนนี้ contract ทำอะไร:** arbiter คือ address เดียว (ตั้งตอน deploy เปลี่ยนได้โดย owner) ถูก snapshot ตอนเปิดข้อพิพาท ถ้าเปลี่ยนทีหลังไม่กระทบข้อพิพาทที่เปิดอยู่ และ **arbiter เป็น client หรือ freelancer ของ escrow นั้นไม่ได้** (revert `ConflictOfInterest`)

**ที่ต้องตกลง:** wallet เดียวหรือ multisig, ขั้นตอนตัดสิน (ใครดูหลักฐาน ดูอะไร), และกรอบเวลา

**แนะนำ:**
- **demo:** wallet เดียวของทีมพอ แต่ **ใช้คนละ wallet กับ client และ freelancer** ตอนทดสอบ เพราะถ้า wallet ที่เป็น arbiter ไปเป็น client ด้วย การฝากเงินจะ revert
- **production:** multisig และมีขั้นตอนตอบสนองที่ทันเวลา ไม่งั้นผลจะเป็นแบ่งครึ่งตามกติกา timeout
- ถ้า UI มีช่องเหตุผลตอนเปิดข้อพิพาท ให้เตือนว่า **ข้อความอยู่บน chain ถาวรและทุกคนอ่านได้** ห้ามใส่ข้อมูลส่วนตัว

### 4.8 ส่งงานช้ากว่า deadline

**ตอนนี้ contract ทำอะไร:** `deadline` คือเส้นตายส่งงาน ส่งหลังเวลาแม้วินาทีเดียวผ่าน contract ไม่ได้ แต่ client ยังปล่อยเงินให้งานที่ส่งช้านอกระบบได้ และ client ขอเงินคืนได้หลัง deadline ถ้ายังไม่ส่งงาน และ **ยังไม่มีฟังก์ชันขยายเวลา**

**ที่ต้องถามทีม:** พอแค่นี้หรือต้องเพิ่มฟังก์ชันขยาย deadline

**แนะนำ:** สำหรับ demo พอแล้ว ให้ UI ตั้ง deadline เผื่อเวลาไว้ (ต้องอยู่ในอนาคตไม่เกิน 365 วัน) และเตือนผู้ใช้ให้ชัดว่า deadline คือเส้นตายส่งงานบน chain หากต้องแก้ ค่อยเพิ่มเป็นฟังก์ชันใหม่แล้ว deploy ใหม่

### 4.9 Milestone และการขอแก้งาน

**ตอนนี้ contract ทำอะไร:** จ่ายก้อนเดียวต่อโปรเจกต์ (escrow หนึ่งก้อน = การส่งมอบทั้งงาน) UI แสดง milestone (mock สร้างให้ 1 งวดยอดเต็ม) และมี flow "ขอแก้ไขงาน → ส่งงานใหม่" อยู่แล้ว ซึ่ง contract รองรับด้วย `requestRevision`:

1. ระหว่างช่วงตรวจรับ client เรียก `requestRevision(escrowId, reason)` → สถานะกลับเป็น `Active` และนับ `revisionCount` เพิ่ม
2. **deadline ใหม่ contract เป็นคนกำหนด** = `max(deadline เดิม, ตอนนี้ + revisionPeriod)` client ตั้งเองไม่ได้ (ไม่งั้น client ตั้งสั้นมากแล้วรอขอเงินคืนได้)
3. freelancer ส่งงานใหม่ด้วย `submitWork` เดิม ช่วงตรวจรับเริ่มนับใหม่
4. **จำกัดจำนวนรอบ** `maxRevisions` (ค่าเริ่มต้น 2) **ต่อ escrow** และไม่รีเซ็ตเมื่อส่งซ้ำ → ส่งงานได้สูงสุด 3 รอบ (รอบแรก + แก้ 2 ครั้ง) ถ้าครบแล้ว client เหลือแค่ปล่อยเงินหรือเปิดข้อพิพาท
5. **หลังเคยส่งงานแล้ว client ขอเงินคืนเองไม่ได้** แม้ freelancer ไม่ส่งงานแก้ทัน (ต้อง `openDispute` ให้ arbiter ตัดสินแบ่งสัดส่วน) เพราะ freelancer ส่งงานไปแล้วอย่างน้อยหนึ่งรอบ ส่วน freelancer ยังยกเลิกคืนเงินหรือเปิดข้อพิพาท (ก่อน deadline) ได้ตามเดิม
6. freelancer แก้งานเองโดยไม่ถูกขอไม่ได้ (กันเปลี่ยนไฟล์ที่ client กำลังตรวจ หรือรีเซ็ตเวลาตรวจรับ)

**ที่ต้องถามทีม:** 2 ครั้ง / 7 วันพอไหม (ปรับตอน deploy ได้ `MAX_REVISIONS` 0–10, `REVISION_PERIOD_SECONDS` 1 วินาที–30 วัน; `0` = ปิดฟีเจอร์) และ UI ต้องแสดงจำนวนรอบที่เหลือกับเวลาที่เหลือให้ทั้งสองฝ่ายเห็น

**ตัวเลือก:**
- **ไม่รองรับใน demo** แสดง milestone เป็นข้อมูลอย่างเดียว ไม่ผูกกับเงินบน chain
- **หนึ่ง milestone = หนึ่ง escrow** ใช้ `projectId` ต่างกันต่องวด (เช่น `id("proj-1:m1")`) ใช้ contract เดิมได้เลย แต่ Backend ต้องผูกหลาย `escrowId` เข้ากับโปรเจกต์เดียว
- **แก้ contract ให้รองรับ milestone** งานใหญ่ ต้องเขียนและทดสอบใหม่

**แนะนำ:** ข้อแรกสำหรับ demo ถ้าทีมอยากโชว์งวดงานจริงให้ใช้ข้อสอง อย่าให้ UI ทำให้ผู้ใช้เข้าใจว่าเงินแบ่งจ่ายเป็นงวดในเมื่อ contract จ่ายก้อนเดียว

### 4.10 Wallet address ของ freelancer และ client

**คืออะไร:** ตอนนี้ไม่มีข้อมูลนี้เก็บไว้ที่ใดเลย แต่ contract ต้องใช้ address ของ freelancer ตอนฝากเงิน และ address ของ client ตอนคำนวณ `escrowId`

**ต้องตัดสินใจ:** เก็บที่ไหน (แนะนำคอลัมน์ `walletAddress` ในโปรไฟล์ผู้ใช้) ให้ใครกรอก (ผู้ใช้กด "เชื่อม wallet" เอง) และถ้าผู้ใช้จ่ายด้วย wallet อื่นที่ไม่ตรงกับโปรไฟล์จะทำอย่างไร

**แนะนำ:** ถือ address ที่ปรากฏใน event `EscrowFunded` เป็นความจริงของ `client` และเก็บ `escrowId` จาก event นั้นไว้กับโปรเจกต์ แทนที่จะคำนวณจากโปรไฟล์ซ้ำ ถ้าจะเข้มขึ้นให้ให้ผู้ใช้เซ็นข้อความยืนยันว่าเป็นเจ้าของ wallet ตอนเชื่อม

### 4.11 ใครคือ "ความจริง" เรื่องสถานะ และ Backend ต้องตรวจก่อนเชื่อ

**ตอนนี้:** ปุ่มส่งงาน/ตรวจรับใน Frontend เรียกแค่ API (ดูหมายเหตุข้อ 7 ในหมวด 3)

**ข้อควรระวังสำคัญของ v2:** `escrowId` ผูกกับผู้ฝาก ดังนั้น **ใครก็ฝากเงินด้วย `projectId` เดียวกับงานจริงได้** (ได้ escrow ที่ไม่มีใครผูกกับงาน) นี่คือข้อแลกเปลี่ยนที่แลกกับการที่ไม่มีใครจอง `projectId` ขวาง client ตัวจริงได้ Backend จึง **ต้องตรวจ event `EscrowFunded`** ว่า `client`, `freelancer` และ `termsHash` ตรงกับงานใน DB ก่อนผูก `escrowId` ถ้าไม่ตรงให้ข้าม

**แนะนำ:** เงินและสถานะ = ตามบน chain (อัปเดต DB จาก event) ส่วนข้อมูลที่ไม่เกี่ยวกับเงิน (ชื่องาน รายละเอียด) = ตาม DB และควรรอ confirmation หลายบล็อกก่อนถือว่าสำเร็จ พร้อมเก็บเลขบล็อกล่าสุดที่ประมวลผลไว้ ดึง event ที่พลาดไปตอนเซิร์ฟเวอร์ล่ม

### 4.12 วิธีเก็บ mapping `projectId` ↔ `bytes32` ↔ `escrowId`

**คืออะไร:** contract ใช้ `bytes32` แต่ระบบมี id เป็นข้อความ และหลังฝากต้องใช้ `escrowId`

**แนะนำ:** ทุกฝั่งใช้สูตรเดียวกัน `projectIdHash = id(project.id)` (ethers v6, คือ keccak256 ของข้อความ) เก็บในตาราง DB เป็นคอลัมน์ `projectIdHash` (unique) และ `escrowId` (ได้จาก event หรือเรียก `computeEscrowId(clientAddress, projectIdHash)`) เพื่อให้ฟัง event แล้วหาโปรเจกต์เจอ

### 4.13 RPC URL ที่ใช้ demo

**คืออะไร:** ที่อยู่ "ประตู" ที่ Backend ใช้ฟัง event และที่ใช้ deploy ส่วน Frontend คุยผ่าน MetaMask อยู่แล้ว

**แนะนำ:** สมัครฟรีกับผู้ให้บริการ RPC (เช่น Alchemy หรือ Infura) สร้าง app เลือก Sepolia แล้วเก็บ URL ใน keystore (`npx hardhat keystore set SEPOLIA_RPC_URL`) ไม่ใส่ในไฟล์ในโปรเจกต์ RPC สาธารณะฟรีมักจำกัดอัตราการเรียก ไม่เหมาะกับ Backend ที่ฟัง event ตลอดเวลา

## 6. เรื่องความปลอดภัย (สั้น ๆ)

- Contract นี้ **ยังไม่ผ่าน audit** ใช้ได้เฉพาะ testnet/demo ห้ามใช้กับเงินจริง
- **private key**: ใช้ wallet ใหม่สำหรับ testnet โดยเฉพาะ ห้ามใช้ wallet ที่มีเงินจริง เก็บใน keystore ห้ามใส่ใน Git หรือ `.env`
- **arbiter มีอำนาจแบ่งเงินในข้อพิพาท** จึงควรเป็น multisig เมื่อขึ้น production
- **ขอแก้งานวนไม่รู้จบ**: จำกัดด้วย `maxRevisions` และ client ตั้ง deadline เองไม่ได้ จึงถ่วงเวลาหรือบีบให้หมดเวลาแล้วขอเงินคืนไม่ได้ แต่ก็ยัง "ปล่อยเงินช้า" ได้ภายในรอบที่เหลือ (ช่วงตรวจรับต่อรอบ + เวลาแก้งาน)
- **owner** เปลี่ยนค่าธรรมเนียม/arbiter/ผู้รับได้ทันที (มี event แจ้ง ควรเฝ้าดู) ก่อน production ควรใช้ `Ownable2Step` และให้ owner เป็น multisig
- `reason` ของข้อพิพาท **อยู่บน chain ถาวร** ใครก็อ่านได้
- ผู้รับที่เป็น contract อาจกวนโดยใช้ gas หมด (ผู้เรียกเสีย gas เพิ่ม) ควรประเมินก่อน production
- ราคา ETH ผันผวนมีผลต่อมูลค่าจริงของค่าจ้างบน mainnet (บน testnet ไม่เป็นปัญหา)
- Backend/Frontend ต้องไม่เชื่อ `amount`, `role` ที่ส่งมาจาก client โดยไม่ตรวจซ้ำ ใช้ค่าจาก chain/DB เป็นหลัก
- เทสต์ผ่านเพียงบอกว่า "สิ่งที่เขียนไว้ทำงานถูก" ยังไม่มี fuzz/invariant test เต็มรูปแบบ ก่อนขึ้น mainnet ควรเพิ่ม ใช้ Slither หรือ Foundry fuzz และให้ผู้เชี่ยวชาญ audit
- ประเด็นกฎหมายและภาษี (ข้อตกลงการใช้งานที่ระบุอำนาจของ arbiter, กฎหมายสินทรัพย์ดิจิทัล) อยู่นอกขอบเขตของโค้ด ควรปรึกษาผู้เชี่ยวชาญก่อนใช้กับเงินจริง

## 7. ขั้นต่อไป

1. **คุยกับทีม** ให้ได้คำตอบข้อ 4.2–4.10 โดยเฉพาะข้อที่แก้ไม่ได้หลัง deploy (`reviewPeriod`, `arbiterTimeout`)
2. **รันในเครื่องก่อน** ใน `smart-contact/`: `npm install`, `npm test`, `npm run deploy:local`
3. **เตรียม Sepolia:** ตั้งค่า keystore (`SEPOLIA_RPC_URL`, `SEPOLIA_PRIVATE_KEY`), ขอ Sepolia ETH จาก faucet, คัดลอก `.env.example` เป็น `.env` แล้วกรอกค่า policy
4. **Deploy:** `npm run deploy:sepolia` เก็บ address และ Chain ID ที่สคริปต์พิมพ์ออกมา
5. **ส่งมอบ:** `npm run export-abi` ได้ `abi/FreelinkEscrow.abi.json` ส่ง ABI + address ให้ Frontend พร้อมรายการแก้ในหมวด 3
6. **ทดสอบกับ Frontend จริง** บน Sepolia ด้วย wallet แยกกันสำหรับ client, freelancer และ arbiter ก่อนโชว์
7. (ถ้าต้องการ) verify source บน Etherscan: `npx hardhat verify --network sepolia ...` (ขั้นตอนนี้ยังไม่ได้ลองกับ Etherscan จริง)
